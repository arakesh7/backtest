1. OHLCV Schema Inversion & Column Offset Across Entire Engine

Area: Data Integrity / Pricing
Affected Files data_manager.py:23-32, 75 | broker.py:97, 182 | analyzer.py:65 | execution_model.py:40
Impact Fatal price distortion: Market orders fill at HIGH; Equity multiplies size by VOLUME; Indicators compute on VOLUME.
Root Cause & Mechanics

In data_manager.py, CSVDataLoader reads columns: ['open', 'high', 'low', 'close', 'volume', 'ts']. Setting df.index = df['ts'] does not drop 'ts' from columns. raw_data.to_numpy() returns a row array with indices: [0: Open, 1: High, 2: Low, 3: Close, 4: Volume, 5: TS].
However, broker.py unpacks this as: ts, o, h, l, c, v = bar. Consequently:

  • ts becomes open price (e.g. 100.0)
  • o (Open) becomes high price (105.0) → All market orders fill at the bar's High!
  • h (High) becomes low price (99.0)
  • l (Low) becomes close price (103.0)
  • c (Close) becomes volume (1000)
  • v (Volume) becomes timestamp string
  • In analyzer.py:65: positions_value = sum(pos.size * data[pos.asset][4]) → multiplies shares by Volume instead of Close price! (e.g., 10 shares × 500,000 volume = 5,000,000 portfolio value!)
Empirical Python Test Verification:
Columns: ['open', 'high', 'low', 'close', 'volume', 'ts']
Numpy row: [100.0, 105.0, 99.0, 103.0, 1000, '2024-01-01 09:15:00']
Result: bar[1] (assigned to Open) is 105.0 (High); bar[4] (assigned to Close) is 1000 (Volume)!
The Fix
Current Buggy Code (data_manager.py)
cols = ['open', 'high', 'low', 'close', 'volume', 'ts']
df = pd.read_csv(file_path, usecols=cols, parse_dates=['ts'])
df['ts'] = df['ts'].dt.strftime('%Y-%m-%d %H:%M:%S')
df.index = df['ts']
# df.to_numpy() leaves columns: open=0, high=1, low=2, close=3, volume=4, ts=5
Correct Code (Standardized Schema)
# Standardize canonical tuple format: (ts, open, high, low, close, volume)
cols = ['ts', 'open', 'high', 'low', 'close', 'volume']
df = pd.read_csv(file_path, usecols=cols, parse_dates=['ts'])

df.set_index('ts', drop=False, inplace=True)
# Reorder explicitly before converting to numpy

2. Temporal Reversal & Memory Corruption in BarHistory Slicing

Area: History / Indicators
Affected Files history.py:30-38 | user_strategies.py:28-34, 461, 511, 626, 711
Impact All technical indicators (SMA, EMA, RSI, BBANDS, ATR) receive reversed/scrambled price series; slices return uninitialized None values.
Root Cause & Mechanics

In BarHistory.__getitem__, slicing is implemented as: idxs = (self.head + np.arange(start, stop, step)) % self.size. When strategies do bars[:], key.indices(self.count) produces start=0, stop=count. Because self.head is the latest added bar, index 0 receives self.head (newest bar), followed by self.head + 1 (oldest bar in the buffer)!

  • Before the buffer fills, self.head + 1 is None (uninitialized numpy memory). Passing this to TA-Lib crashes or yields NaNs.
  • When full, the returned array begins with the newest bar, jumps to the oldest bar, and counts upward. closes[-1] is actually bar[-1] (yesterday's bar), and closes[0] is the current bar!
  • Slicing history[-10:] evaluates in Python as indices(count) -> [count-10 ... count-1], which shifts by head, completely skipping the current bar!
Empirical Python Test Verification:
Buffer of size 5 with bars 0 to 4 added:
bh[:] = ['bar_4', 'bar_0', 'bar_1', 'bar_2', 'bar_3'] ← Newest bar at front, oldest follows!
bh[-1] = bar_3 ← TA-Lib calculating EMA on bh[:] uses bar_3 as latest price, not bar_4!
The Fix
Current Buggy Code (history.py)
def __getitem__(self, key):
    if isinstance(key, int):
        return self.get(key)
    elif isinstance(key, slice):
        start, stop, step = key.indices(self.count)
        idxs = (self.head + np.arange(start, stop, step)) % self.size
        return self.data[idxs]
Correct Code (Chronological Circular Unwrapping)
def __getitem__(self, key):
    if isinstance(key, int):
        return self.get(key)
    elif isinstance(key, slice):
        start, stop, step = key.indices(self.count)
        # Oldest stored bar is at physical index: (self.head - self.count + 1) % self.size
        base = self.head - self.count + 1
        idxs = (base + np.arange(start, stop, step)) % self.size
        return self.data[idxs]

3. Inverted Cash Accounting: Partial Sells Burn Cash, Covers Print Cash

Area: Broker / Accounting
Affected Files order.py:124-145 | broker.py:118-156
Impact Taking profit on partial exits drains cash; covering shorts creates free cash; position flips calculate false PnL and retain wrong entry prices.
Root Cause & Mechanics

In order.py, Position.update(size, price) handles position decreases as: opened, closed = 0, size. When selling 5 shares from a 10-share long position: size = -5. Thus closed = -5. In broker.py: close_value = closed * fill_price = -5 * 120 = -600. cash_in = close_value = -600. self.cash += cash_in → Subtracts $600 from cash instead of crediting $600!
Conversely, when partially covering a short (position -10, buy 5), size = +5, so closed = +5, cash_in = +400, adding $400 to cash instead of spending $400.
Furthermore, flipping a position (e.g. Long 10, Sell 15 to flip to Short -5) enters the decrease branch: it books realized PnL on 15 shares (instead of 10), and fails to reset avg_price for the new -5 short position.

Empirical Python Test Verification:
Buy 10 @ 100 → Cash = 9,000, Position = 10.
Sell 5 @ 120 (Partial close) → Expected Cash: 9,600. Actual Cash: 8,400!
Selling for a profit caused cash to drop by $600!
The Fix
Current Buggy Code (broker.py & order.py)
# broker.py
opened, closed, _, _ = position.pseudo_update(size, fill_price)
open_value = opened * fill_price
close_value = closed * fill_price
cash_in = close_value
cash_out = open_value + commission
self.cash += cash_in
self.cash -= cash_out
Correct Code (Universal Cash Flow & Position Transition)
# Cash flow is universally: - (order_size * fill_price) - commission
# (Positive for SELL, Negative for BUY)
trade_cash_delta = -(size * fill_price) - commission
if order.side == "BUY" and abs(trade_cash_delta) > self.cash:
    order.status = "REJECTED"
    return None

self.cash += trade_cash_delta
# Cleanly split position updates into:
# 1. Closing existing portion (at old avg_price)
# 2. Opening new portion (at new fill_price if position flips)

4. Lookahead Bias & Bar-Path Dependency in Stop Loss / Take Profit

Area: Strategy / Execution
Affected Files user_strategies.py:209-231, 261-266 | top_momentum_orb_strategy.py:197-225, 298-335
Impact Exits fill at next bar's Open rather than SL/TP; breakout entries log idealized fill prices; simultaneous SL/TP breaches handled with optimistic bias.
Root Cause & Mechanics

In existing strategies, risk management is implemented inside on_data rather than inside the broker. When curr_low <= sl is detected, the strategy calls self.close(symbol), which queues a Market Order. This market order does not execute on the current bar—it executes on the next bar's Open. However, the strategy deletes self._pos_details[symbol] immediately on the current bar.
In top_momentum_orb_strategy.py, breakout entries do: if curr_high > or_high: entry = or_high; self.buy(symbol, entry_price=entry). Because self.buy creates a MARKET order by default, the trade executes at the next bar's Open, yet the strategy logs and calculates SL/TP as if it entered exactly at or_high.
Additionally, when a volatile candle breaches both SL and TP in the same bar, the code evaluates whichever if condition appears first, ignoring intra-bar tick sequencing.

The Fix

Stop losses and Take Profits must be native broker order types (SL and LIMIT). When submitted as a bracket order, the broker must check price penetration within the bar: if Low ≤ Stop Price, fill at min(Open, Stop Price) (accounting for gap downs) within that exact bar. If both SL and TP are penetrated within the same bar, assume the conservative worst-case (Stop Loss hit first).

Affected Files analyzer.py:82, 105-113, 125-149

4. Holiday Valuation Drop: When exchange holidays are missing from data, positions_value drops to 0 on that bar, fabricating catastrophic artificial drawdowns.

Area: Broker / Order Queue
Affected Files broker.py:33-56, 71-80
Impact Concurrent signals size against the same free cash; trade execution order is non-deterministic (based on dictionary order).
Root Cause & Mechanics

When a multi-asset strategy generates buy signals on 3 assets on the same bar, each order sizes against the current cash balance.
